프로젝트 개요

팀 협업 중에는 한 작업을 멈추고 다른 이슈를 처리할 때 현재 브랜치의 파일 변경을 stash에 넣고, 새 브랜치에서 다시 꺼내는 일이 반복됐습니다. Taskflow는 이슈 선택부터 브랜치 준비, 검사, PR 생성까지를 연결하는 개인 도구입니다. 파일 변경과 커밋이 다른 작업에 섞일 위험이 있으면 이동 전에 멈추도록 설계했습니다.

작업 흐름

  • 작업 시작

    이슈를 선택하고 작업 브랜치를 준비한 뒤 현재 저장소 상태를 확인합니다.

  • 변경사항 이어가기

    기준 브랜치의 커밋 이력과 원격 상태를 확인한 경우에만 기존 파일 변경을 새 작업 브랜치로 가져옵니다.

  • 검증과 PR

    정해진 검사와 선택한 stage, commit, push, PR 단계를 이어갑니다. 상태가 불분명하면 파일을 바꾸기 전에 사용자에게 확인을 요청합니다.

제가 맡은 일

협업 중 반복되던 인계 절차를 워크플로 스킬과 Python 런타임으로 구현했습니다. 기준 브랜치의 원격 이력과 작업 트리 상태를 확인해 변경사항을 이어갈 수 있는 조건을 정했습니다. 현재 변경사항을 자동으로 stage하거나 강제로 reset하지 않으며, 안전한 상태인지 설명할 수 없으면 실행을 중단합니다.

선택한 안전 기준 · 확실하지 않으면 변경하지 않습니다

이 도구의 자동화 범위는 브랜치 전환 자체보다 현재 작업을 다른 이슈의 PR에 섞지 않는 데 맞췄습니다. 기준 원격 브랜치가 확인되고 현재 HEAD가 그 이력에 속하는지 검사한 다음에만 변경사항을 이어갑니다.

조건이 확인되면 진행

원격 기준 브랜치와 Git 이력이 예상한 상태라면 현재 파일 변경을 보존해 새 작업 흐름으로 넘기고 검사·PR 단계로 이어갑니다.

상태가 모호하면 중단

원격 기준이 없거나 현재 커밋이 기준 브랜치의 이력이 아니면 자동 이동하지 않습니다. 작업 파일·Stage·커밋을 그대로 두고 사용자가 먼저 확인하게 합니다.

자동으로 복구해 주는 편의는 줄었지만, 로컬 커밋이나 다른 브랜치의 작업이 새 PR에 섞일 가능성을 낮춥니다. 실제 Git 상태를 사용한 검증은 아래에 따로 표시했습니다.

검증과 배운 점

실제 Git 상태

임시 저장소와 bare remote를 만들고 Git 명령으로 인덱스, 브랜치, 원격 기준을 확인했습니다.

테스트 18개

파일 변경 보존, 기준 브랜치 보호, 위험 상태에서의 중단을 다뤘습니다.

Python 컴파일 검사와 테스트는 GitHub Actions에서 통과했습니다. 외부 GitHub 호출만 fake CLI로 대체했으므로 인증 오류와 네트워크 장애는 검증 범위에 포함되지 않습니다.

자동화는 단계를 줄이는 것만으로 안전해지지 않았습니다. 실행 전에 기준 브랜치와 이력을 확인하고, 예상하지 못한 상태에서 멈추는 조건을 함께 정해야 했습니다.
