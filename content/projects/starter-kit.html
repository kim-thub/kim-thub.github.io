프로젝트 개요

새 AI 서비스를 시작하면 모델 호출과 문서 검색, API 연결, 로컬 실행 환경을 각각 준비해야 합니다. 이 프로젝트는 반복되는 기반 기능을 저장소 안의 공통 모듈로 묶고, 개발자가 전체 예제 앱이나 LLM CLI, RAG CLI 중 필요한 범위만 실행하게 합니다. RAG는 문서에서 근거를 찾아 모델 답변에 활용하는 방식입니다.

스타터킷이 제공하는 것

  • 필요한 범위만 실행

    전체 예제 앱, LLM CLI, RAG CLI 중 목적에 맞는 프로필을 선택합니다.

  • 문서 처리와 검색

    PDF는 모델 입력 상한을 넘지 않도록 나누고 원문 누락 여부를 확인합니다. XLSX는 행 단위로 보존하며 출처 검토, 색인, 게시, 검색을 지원합니다.

  • 환경과 모델 준비

    운영체제별 시스템 의존성을 점검하고 설치 방법을 안내합니다. 로컬 환경 설정(env)과 EmbeddingGemma 2 모델 이미지 패키징도 포함합니다.

공통 모듈은 이렇게 연결됩니다

화면의 요청을 Backend가 받고, 필요한 기능만 LLM·RAG 모듈의 공개된 Port를 통해 호출합니다.

문서 유형에 따라 다르게 처리합니다

PDF 본문과 스프레드시트 행은 자연스러운 정보 단위가 달라 같은 방식으로 자르지 않았습니다. 문서 종류별로 실제 적용한 처리와 확인 범위를 나눴습니다.

PDF · 본문 흐름 보존

토큰 상한 안에서 분할하고 원문을 대조

  1. 본문 추출Docling으로 읽은 일반 문서 요소를 토큰 상한에 맞춰 준비합니다.
  2. 안전한 경계 찾기문서를 최대 512 토큰 단위로 나누며, 어절 중간이 아닌 띄어쓰기 위치에서 구간을 나누도록 주의합니다.
  3. 원문 무결성 확인분할 조각을 이어 붙여 원문과 일치하는지 검사하고 다르면 색인을 중단합니다.
XLSX · 행 단위 정보 보존

행을 나누지 않고 출처와 함께 보존

  1. 행을 정보 단위로 취급셀 사이 관계를 잃지 않도록 긴 행도 통째로 유지합니다.
  2. 출처 위치 연결검색 근거에서 원본 시트와 행 범위를 다시 찾을 수 있게 기록합니다.
  3. 관측 결과와 한계 구분사용한 Source_V3에는 512 토큰을 넘는 행이 없었기 때문에 더 긴 행은 실활용 시 생길 수 있는 한계입니다.
검토 자료 게시 전

사람이 검토한 문서만 색인 대상으로 승인했습니다. 청크 수, 원본/승인 해시, 출처 정보가 일치하는지 검증하고 문제가 없을 때만 검색 가능한 published 상태로 전환했습니다.

제가 맡은 일

RAG와 문서 처리

청킹 방식과 입력 예산을 비교하고, PDF 분할과 원문 무결성 검사를 구현했습니다. HITL을 이용한 파싱 검토와 흐름을 검증했습니다.

로컬 실행 기반

bootstrap 실행 프로필, 암호화된 로컬 비밀 설정, EmbeddingGemma 2 이미지 패키징을 맡았습니다.

확인한 결과와 배운 점

RAG 검색 품질

Hit@10 90.4%

상속길잡이의 초기 기술검증에서는 네 가지 청킹 방식을 비교해 표의 각 행을 독립적으로 처리하는 방식을 선택했습니다. 이후 실제 근거 데이터와 검증 질문 26개를 원문과 의미를 구체화한 문장으로 각각 검색해 총 52회 평가했습니다. MRR@10은 0.824였으며, 최종 구성에서는 승인된 근거가 누락되지 않는지도 함께 확인했습니다.

1.045 GB → 0.365 GB

EmbeddingGemma 2 패키징에서 가장 큰 압축 OCI 레이어 크기입니다. 전체 이미지 크기는 거의 달라지지 않았습니다.

청킹 선택의 근거와 가정

문장·단어 단위보다 토큰 사이 관계를 더 잘 잇기를 기대해 Agentic을 MVP 1로 선택했습니다. 관계 보존을 별도 지표로 확인한 것은 아니며, 이 비교만으로 일반적인 검색 품질을 주장하지 않습니다.

설치 자동화의 경계

PostgreSQL, pgvector, Ollama는 운영체제마다 설치 방법과 권한이 달라 bootstrap을 통한 자동 설치를 구현하지 않았습니다. 대신 설치 여부와 안내를 제공하므로 사용자가 환경에 맞는 설치를 직접 해야 하는 번거로움은 있습니다.
