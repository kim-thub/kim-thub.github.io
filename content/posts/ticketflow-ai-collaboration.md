# TicketFlow를 만들 때 AI를 어떻게 활용했는가

TicketFlow는 접속자가 한꺼번에 몰려 서버가 불안정해지는 티켓 예매 환경을 비슷하게 구현하고, 고동시성 개발을 연습하려고 만든 시스템이다. 기획과 설계부터 Go API, Redis Lua 스크립트, 테스트 코드, 화면까지 AI를 활용해 구현했다. 구현한 뒤에는 5만 명과 10만 명이 실제로 좌석을 두고 경쟁하는 시험으로 동작과 정합성을 확인했다.

평소에도 요구사항과 정책을 먼저 검토하고 AI에 구현을 맡긴 뒤 실행 결과를 직접 확인하는 방식으로 작업해 왔다. TicketFlow에서는 대기열, 좌석 선점, 결제 후처리와 부하 시험까지 다루면서 평소의 작업 방식을 더 구체적으로 정리할 수 있었다. 특히 테스트가 실패했을 때 어떤 근거로 수정 방향을 정했는지 기록하려고 한다.

## 요구사항부터 정한 다음 구현을 요청했다

대기열이 있는 공연 예매 시스템을 만들려면 예상보다 많은 정책을 정해야 했다. 같은 사용자가 다시 대기열에 들어오면 어떻게 처리할지, 입장권 활성화 응답이 유실됐을 때 무엇을 반환할지, 여러 사용자가 같은 좌석을 선택하면 누가 선점하게 할지부터 검토했다. 결제 이후 Worker가 멈췄다가 복구되는 경우도 설계에 포함했다.

나는 코드를 요청하기 전에 AI와 대안을 비교한다. 어느 방안이 단순한지, 장애 상황에서 어떤 문제가 생기는지, 정합성을 지키려면 어떤 제약이 필요한지 검토한 뒤 정책을 결정한다. TicketFlow에서도 Redis가 대기 순서와 입장 토큰을 관리하고, PostgreSQL이 좌석과 예약의 최종 상태를 결정하도록 나눴다. 결제 이후 발권과 환불은 Kafka 이벤트를 이용했다.

구현 과정에는 `grill-me`, `$superpowers`, `@ponytail` 스킬을 사용했다. `grill-me`로 미처 정하지 않은 설계 조건을 질문으로 확인하고, `$superpowers`로 작업을 계획하고 검증했다. `@ponytail`은 불필요한 추상화와 복잡한 구조가 들어가지 않았는지 검토할 때 활용했다. 최종 정책은 스킬의 제안을 검토한 뒤 직접 결정했다.

합의한 결정은 ADR(아키텍처 결정 기록)에 남겼다. 이미 승인한 정책을 변경하면 기존 ADR을 고치는 대신 새 ADR을 작성하고 변경 사유를 기록했다. 시간이 지난 뒤에도 당시 어떤 조건을 보고 그 구조를 선택했는지 확인하기 위해서다.

## 코드 수정 요청에는 유지할 계약도 적었다

Go API, Worker, Redis Lua 스크립트, 화면, 테스트 코드는 AI가 작성했다. 생성된 코드는 로컬 Docker Compose 환경에서 실행했고, 테스트가 실패하면 로그와 함께 기대하는 동작을 전달했다. 이때 실패한 파일만 고치지 말고 같은 계약을 사용하는 호출부와 테스트도 확인하도록 요청했다.

한 곳을 수정한 뒤 다른 테스트가 깨지는 문제도 발생했다. 동시성 시스템에서는 어떤 동작을 유지해야 하는지 명확히 적지 않으면 수정 범위가 어긋나기 쉬웠다. 입장 토큰을 새로 발급하는 것과 이미 발급한 토큰을 다시 조회하는 것을 구분해야 했던 사례가 대표적이다.

## 입장권 재시도 계약과 충돌한 테스트

사용자가 입장권 활성화에 성공했더라도 HTTP 응답을 받지 못할 수 있다. 이때 같은 사용자와 같은 클라이언트가 다시 활성화를 요청하면 유효한 기존 토큰을 그대로 반환하도록 정책을 정했다. 재요청 때문에 토큰의 만료 시각이 늘어나서는 안 되고, 다른 클라이언트에 토큰을 전달해서도 안 됐다.

그런데 기존 테스트에는 활성화를 반복 요청하면 토큰을 반환해서는 안 된다는 기대값이 남아 있었다. Go 테스트에서 다음 오류가 발생했다.

```text
--- FAIL: TestAdmissionUnauthorizedClientCannotActivate
    admission_contract_test.go:219:
    repeated activation must not return replacement token
```

오류 메시지만 보면 토큰을 반환한 서버 동작이 잘못된 것처럼 보인다. 그러나 같은 사용자와 클라이언트의 재요청에는 기존 토큰을 돌려주는 것이 당시 승인한 계약이었다. 다른 클라이언트에 토큰을 전달하거나 만료 시각을 연장하는 행위는 여전히 막아야 했다. 서버와 테스트 중 어느 쪽이 계약과 다른지 먼저 확인할 필요가 있었다.

테스트를 수정할 때에는 기존 토큰 재사용은 허용하되 비인가 클라이언트, 위조 토큰, 만료된 세션은 계속 거절하도록 했다. 같은 계약을 참조하는 테스트도 함께 확인했다. 당시에는 다음과 같이 요청했다.

> "이번에는 전체 테스트 코드를 전수 조사하고, 비슷한 오류가 발생할만한 코드를 전부 수정해줘."

이 사례에서도 테스트 하나가 통과했다는 보고만으로 수정을 끝내지 않았다. 영향받는 테스트를 다시 실행하고, 승인한 계약이 유지되는지 확인했다.

## 부하 실험에서는 AI가 작성한 평가기도 확인했다

기능 코드가 동작한다고 해서 검증 코드까지 올바른 것은 아니었다. 초기에는 k6의 `--summary-export` 파일을 읽는 Python 코드가 출력 형식을 잘못 가정했다. 일부 지표가 `values` 아래에만 있을 것으로 예상했지만, 사용한 k6의 출력에는 `count`나 `rate`가 직접 들어 있는 항목도 있었다. 그 결과 값이 `null`로 처리되고 필요한 감사가 실행되지 않았다.

원본 기록으로 파싱 오류를 확인하고 집계 코드를 고쳐 다시 계산했다. 이후에는 시험을 실행하기 전에 요약 파일에서 필수 지표를 정확히 읽는지부터 검토했다.

실제 부하가 제대로 발생했는지도 별도로 봐야 했다. 한 초기 시험에서는 90,000회 시도를 계획했지만 완료된 작업은 67,401회였고, 22,602회가 드롭됐다. 이 상태에서 일부 HTTP 요청이 성공했다는 이유만으로 성능 목표를 충족했다고 판단할 수는 없다. 부하 발생기의 작업 누락, DB에 커밋된 HOLD, 결과가 확인되지 않은 사용자, 수집되지 않은 표본을 각각 구분하도록 요청했다.

평가기의 파싱 오류를 고쳤어도 부하가 제대로 발생하지 않았다면 성능 측정 결과를 믿을 수 없었다. 그래서 결과를 판정하는 코드와 실제 요청 실행 기록을 따로 확인했다.

## PASS를 내리기 전에 무엇을 검사할지 정했다

성능과 정합성 판정에서도 같은 방식으로 AI가 생성한 코드의 입력과 분모를 확인했다. 예를 들어 성공 HOLD TPS를 전역 카운터로 계산하면 다른 공연의 선점 결과가 섞일 수 있다. 따라서 공연별 PostgreSQL 커밋 수와 실제 측정 시간을 대조하도록 했다. 입장 허용 건수나 HTTP 요청 수를 성공 HOLD TPS라고 부르지 않는 것도 같은 이유였다.

정합성 판정에는 또 하나의 조건을 넣었다. 증거가 일부 누락됐더라도 **이미 확인된 위반이 있으면 FAIL**이어야 한다는 것이다. `scripts/evaluate-slo.py`에는 다음 분기가 있다.

```python
for key,limit in slo['invariants'].items():
    if key not in inv or type(inv[key]) is not int or inv[key] < 0:
        missing_invariants.append(key)
    elif inv[key]>limit:
        violations.append(key)

if violations:
    return {'verdict':'FAIL','reason':'invariant_violation','violations':violations,
            'missing_invariants':missing_invariants}
```

확인된 중복 예약 위반이 있다면 다른 자료가 부족하다는 이유로 판정을 미룰 수 없다. 반대로 위반이 관측되지 않았어도 필요한 원장이 없다면 모든 조건을 통과했다고 말할 수 없다. 그래서 평가기는 `PASS`, `FAIL`, `INCOMPLETE`를 구분한다.

## 코드 동결과 공개 준비에도 같은 기준을 적용했다

후반에는 기능을 추가하는 것보다 검증한 범위를 유지하는 일이 중요해졌다. 이미 확인된 운영 코드를 문서 작업 때문에 다시 수정하면 새로운 회귀가 생길 수 있었다. 그래서 서비스 코드와 독립 감사 도구를 구분하고, 코드를 동결한 뒤에는 불필요한 로직 변경을 피했다.

원본 실행 로그와 당시 판정은 보존했다. 부족한 증거를 나중에 다시 분석할 수는 있어도 과거 시험의 실패를 소급해 성공으로 바꾸지는 않았다. 공개할 코드의 파일 목록과 해시를 대조하고, 자격 증명이나 비공개 검증 자료는 공개 대상에서 분리했다.

## 계속 다듬어 갈 AI 활용 방식

TicketFlow에서도 평소와 같이 요구사항과 예외를 먼저 정하고, 대안을 비교한 뒤 AI가 작성한 코드를 실행해 확인했다. 이번에는 동시성 오류와 부하 시험을 다루면서 기능 코드뿐 아니라 테스트와 평가기가 올바른지도 함께 살펴야 했다.

가장 많은 시간을 들인 성능 목표는 **성공 HOLD 1,000 TPS**였다. 목표를 검증하기까지 코드와 시험 조건, 집계 방식을 반복해서 점검했다. 이 과정은 AI에 무엇을 요청할지뿐 아니라 결과를 어떤 근거로 판단할지 정하는 일의 중요성을 다시 확인한 경험이었다.

앞으로도 새로운 AI 도구와 스킬을 계속 익히고 실제 프로젝트에 적용해 볼 생각이다. 잘 맞는 방법은 이어 가고, 그렇지 않은 방법은 사용하면서 고쳐 나가려고 한다.
