# 네이버 SDD 도입기를 보고 시작한 TreshCheck 하네스 ⛓︎

네이버 D2의 ‘우리 팀만의 스펙 주도 개발 정착기’를 보고 TreshCheck의 첫 하네스를 만들었다. 하네스는 AI가 개발할 때 참고하는 프로젝트 규칙과 작업 기록이다. 나는 영상에서 본 스펙 주도 개발(SDD)의 흐름을 프로젝트에서 반복할 규칙으로 정리했다.

처음 정한 SDD 규칙만으로는 실제 개발에 필요한 내용이 다 담기지 않았다. 빌드 산출물 경로, 기존 API 계약과 테스트 범위, 중요한 결정의 승인, 검증 결과 기록처럼 프로젝트에 맞는 규칙을 하나씩 추가했다. 이 글은 첫 하네스에서 현재 구조까지 무엇을 더했고, 왜 바꿨는지 돌아본 기록이다.

## 첫 하네스의 출발점은 네이버 SDD 정착기

네이버 D2 영상은 SDD를 팀의 개발 정책으로 삼은 배경과 시행착오를 다룬다. 나는 영상을 보고 요구사항과 설계를 먼저 정리하고, 계획과 결정을 기록한 다음 구현과 검증으로 이어지는 순서를 프로젝트 규칙으로 삼았다. 매번 같은 기준을 설명하지 않아도 되고 그러면 개발도 수월해질 거라고 생각했다.

## 실제 작업에서 필요한 규칙이 더 생겼다

SDD의 기본 흐름을 정한 뒤에도 실제 작업에서 필요한 규칙이 계속 드러났다.

1. 백엔드 빌드 결과물이 `backend/bin/`에 만들어지는 문제를 겪었다. 같은 문제가 반복되지 않도록 저장소 공통 지침인 `AGENTS.md`에 `backend/gradlew`로 빌드하고 결과물은 `backend/build/`에 두라고 적었다. 잘못 만들어진 `backend/bin/`을 정리하는 방법도 함께 기록했다.
2. API 계약과 기존 기능을 함께 다루면서 변경할 부분만 적어서는 부족하다는 걸 알았다. 유지할 요청·응답 구조, 데이터 원본, 오류 처리, 테스트 범위도 계획에 적었다. 선택이 필요한 내용은 대안과 근거를 나눠 기록하고, 중요한 결정은 적용 전에 확인받도록 했다. 검증을 실행하지 못했으면 통과로 적지 않고 `NOT RUN`이나 `BLOCKED`로 남겼다.

이런 요구가 쌓여 11월 17일에는 작업마다 작성하던 계획과 결정 기록의 공통 형식을 `rules/SDD.md`에 정리했다.

현재 `rules/SDD.md`는 코드 수정 전에 같은 저장소에 `plan.md`와 `decisions.md`를 작성하도록 정한다. 계획에는 작업 배경, 범위, 구현 단계, 검증 방법, 선행 조건, 용어, 후속 작업을 적는다. 결정 기록에는 문제, 대안, 선택, 근거를 남긴다. 중요한 결정은 사람이 확인한 뒤 적용한다.

작업별 계획과 결정은 `specs/` 아래에 둔다. 승인이 필요한 작업에는 `approvals.json`을 남기고, 검증 결과도 작업별 문서에 기록한다. 큰 작업은 `implementation-plan.md`에 세부 구현 항목을 적는다.

이 구조는 별도 실행 코드가 아니라 문서로 만들었다. 공통 절차와 `plan.md`, `decisions.md`에 적을 항목은 `rules/SDD.md`에 두고, 작업별 범위와 결정은 `specs/<작업명>/`에 남긴다. 카탈로그 미리보기 계획에는 Preview API가 업무 DB를 쓰지 않는 조건과 프런트엔드·API 변경 제외 범위를 적고, CSV 파서 선택은 별도 결정 기록에 근거와 함께 남겼다. 결정이 바뀔 때는 기존 기록을 덮어쓰지 않고 새 `Dec-N`을 추가해 `supersedes`로 이전 결정과 연결한다. 반복해서 설명할 기준과 선택이 바뀐 이유를 각각 다시 찾을 수 있다.

```text
rules/
  SDD.md                         # 모든 작업이 따르는 공통 규칙
specs/
  2026-11-16-backend-catalog-preview-v1/
    plan.md                      # 이 작업의 배경, 범위, 검증 기준
    decisions.md                 # 이 작업에서 고른 대안과 이유
    approvals.json               # 결정 승인 기록
    verification.md              # 실제 확인 결과
```

```md
# specs/2026-11-16-backend-catalog-preview-v1/plan.md
## Scope
**In**
- Preview API는 판정과 요약을 반환하고 업무 DB를 쓰지 않는다.

**Out**
- Frontend 수정
- OpenAPI 경로와 DTO 변경

---

# specs/2026-11-16-backend-catalog-preview-v1/decisions.md
## Dec-001 — CSV 파서 선택
문제: 원본 CSV를 안전하게 읽어야 한다.
대안: Apache Commons CSV 사용 또는 파서 직접 작성
선택: Apache Commons CSV 사용
근거: 표준 CSV 라이브러리로 인용 필드 처리를 맡긴다.
```

모든 작업에서 문서를 자동으로 읽게 하지는 않았다. 토큰을 아끼려고 SDD 작업에 필요한 공통 규칙과 해당 작업의 스펙만 골라 읽거나 전달했다.

## 실제 작업에서 이렇게 썼다

먼저 관련 코드와 API 계약을 읽고 바꿀 부분과 유지할 부분을 계획에 적었다. 설계에 선택지가 있으면 대안과 근거를 기록하고 사람의 승인을 받았다. 승인된 범위에 맞춰 작업을 나눴다. 단계가 끝날 때마다 테스트나 실제 실행 결과를 남겼다. 검증을 실행하지 못한 경우에는 `NOT RUN`이나 `BLOCKED`로 기록했다.

카탈로그와 접수 미리보기 작업 계획에는 기존 API 계약, CSV 원본, 검색 방식, DB에 쓰지 않는 조건을 적었다. 사용할 라이브러리와 갱신 간격처럼 정하지 않은 항목은 결정 기록으로 분리했다. 구현할 때는 이 기록에서 작업 범위와 예외 조건을 확인했다.

2026년 11월 17일, Preview API 요청 10건으로 RAG를 평가했다. 9건은 근거를 찾아 응답했고(`GROUNDED`), 1건은 자료를 찾지 못해 `NO_EVIDENCE`를 반환했다. 자료 저장과 지역별 출처 격리는 통과했다. `GROUNDED`는 근거를 찾았다는 뜻일 뿐 답변이 질문에 맞았다는 뜻은 아니기에 근거 응답 9건 중 질문의 세부 주제에 맞는 답은 2건뿐이고, 나머지 7건은 다른 내용을 답했다고 볼 수 있다. 답변 주제 적합성은 통과하지 못했다고 기록하고 검색 개선을 후속 작업으로 남겼다.

## 영상에서 가져온 첫 구조와 현재 상태

| 구분 | 첫 하네스 | 현재 하네스 |
|---|---|---|
| 기본 방향 | 네이버 SDD 도입기를 참고해 반복 가능한 SDD 흐름을 고정 | 같은 흐름에 TreshCheck의 저장소 규칙과 검증 기준을 추가 |
| 작업 기록 | 요구사항, 설계, 계획, 결정, 검증을 일정한 순서로 기록 | `specs/`에 범위, 대안, 승인, 실행 결과를 더 구체적으로 기록 |
| 프로젝트 제약 | 일반적인 SDD 절차 중심 | `AGENTS.md`에 빌드 경로와 산출물 규칙을 명시 |
| 결과 확인 | 계획한 검증으로 구현을 확인 | 실제 실행 결과와 `NOT RUN`, `BLOCKED`를 구분해 기록 |
| 작업 분담 | 서브에이전트 흐름은 포함하지 않음 | 서브에이전트 위임과 실행 전 모델 선택은 후속 개선으로 남김 |

## 더 좋은 하네스로!

지금 방식은 작업 계획과 범위를 정리하는 데는 도움이 된다. 하지만 세부 작업을 자동으로 나눠 맡길 수 없어 내가 에이전트 창을 따로 열어 작업을 나눠야 했다. 앞으로는 개별 작업을 서브에이전트가 맡아 실행하게 하고 싶다.

가끔 자동으로 작업을 맡기면 작은 일에도 뱁새 주제에 황새 같은 고사양 모델이 배정된다. 내 토큰을 모조리 써버리면 다시 수작업 개발자로 돌아가야 한다. 이를 막으려고 서브에이전트를 실행하기 전에 나에게 사용할 모델을 먼저 묻도록 하려 한다.

하네스는 실제 작업에서 반복된 규칙과 결정을 문서로 옮겨, 같은 내용을 매번 설명하지 않고도 작업 범위와 검증 결과를 다시 찾으려고 만들었다. 앞으로도 개발 중 드러나는 문제를 기록하고 필요한 규칙을 더하며 다듬고 싶다.
