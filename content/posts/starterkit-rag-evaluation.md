# 상속길잡이 스타터킷의 청킹 평가와 원문 보존

## 검색 순위와 입력 예산을 함께 확인했습니다

RAG를 구현하기 전, Document, Fixed-size, Recursive, Sentence, Semantic, Agentic의 여섯 가지 청킹 방식을 학습했습니다.

이후 문서 파싱 도구로 Docling을 선택하면서 실제 데이터에 어떤 청킹 방식이 적합할지 확인할 필요가 있었습니다.

Docling에서 제공하는 Hierarchical, Hybrid, LineBased 세 가지 방식과 직접 구현한 행 단위 청킹을 비교했습니다. 출처가 연결된 27개 행을 대상으로, Golden Set 45개 질문 중 근거를 연결할 수 있는 6개를 선정해 검색 결과를 평가했습니다.

| 방식 | Recall@5 | MRR@10 | 512 토큰 안에서 사용 가능한 근거 |
|---|---:|---:|---:|
| 행 단위 custom 처리 | 77.8% | 0.660 | 41.7% |
| Hybrid | 66.7% | 0.478 | 5.6% |
| LineBased | 66.7% | 0.478 | 5.6% |
| Hierarchical | 100% | 1.000 | 0%, 단일 6,971 토큰 청크 |

Recall@5는 정답 근거가 상위 5개 검색 결과에 포함된 비율이고, MRR@10은 정답 근거가 상위 10개 결과 중 얼마나 앞에 나타나는지를 반영하는 지표입니다.

Hierarchical은 Recall@5와 MRR@10에서 가장 높은 점수를 기록했습니다. 하지만 숫자만 보고 판단할 수는 없었습니다. 검색 결과가 6,971토큰의 단일 청크였기 때문입니다. 여러 정보가 하나의 청크에 묶이면서 높은 점수를 기록했지만, 정작 512토큰 입력 예산에는 들어오지 않았습니다.

Hybrid와 LineBased는 입력 예산 안에서 사용할 수 있는 근거가 각각 5.6%에 그쳤습니다.

반면 행 단위 커스텀 청킹은 Recall@5가 77.8%, MRR@10이 0.660이었고, 입력 예산 안에서 사용할 수 있는 근거의 비율도 41.7%로 가장 높았습니다.

### 실험 결과를 실제 구현에 반영하기까지

Docling의 세 가지 방식은 이번 데이터에서 기대에 미치지 못했습니다. 특히 XLSX 자료는 한 행에 출처와 관련 정보가 함께 담겨 있어, 행을 여러 조각으로 나누는 방식이 적절하지 않다고 판단했습니다.

따라서 XLSX에는 한 행을 하나의 정보 단위로 유지하는 커스텀 청킹을 적용했습니다. 문서 구조를 활용하면서 필요한 정보를 함께 보존하기 위한 선택이었습니다.

일반 문서를 위한 기본 청킹 전략으로는 Agentic을 선택했습니다. 학습했던 방식 중 문맥과 정보 간 관계를 보존하는 데 적합할 것으로 판단했기 때문입니다.

## PDF 토큰 초과 문제와 분할

PDF 처리 과정에서는 512토큰을 초과하는 청크가 생성되어 후속 검증과 색인 단계에서 오류가 발생했습니다.

이를 해결하기 위해 문서 요소를 토큰 상한에 맞춰 나누도록 수정했습니다.

문자 수와 토큰 수는 항상 비례하지 않습니다. 따라서 문자를 일정한 길이로 자르는 대신, 실제 토큰 수를 계산하면서 나눌 위치를 찾아야 했습니다.

아래 코드는 이진 탐색으로 토큰 상한을 넘지 않는 가장 긴 구간을 찾는 부분입니다.

```python
low = 1
high = len(remainder)
best = 0

while low <= high:
    middle = (low + high) // 2
    candidate = remainder[:middle]

    if _validate_token_count(count_tokens, candidate) <= target_tokens:
        best = middle
        low = middle + 1
    else:
        high = middle - 1
```

문자열의 중간 지점부터 토큰 수를 확인하고, 상한을 넘으면 탐색 범위를 줄이고 여유가 있으면 늘렸습니다.

이렇게 찾은 구간 안에서 가능하면 공백이나 줄바꿈을 기준으로 나눴습니다. 단어와 문장이 불필요하게 끊기는 일을 줄이기 위해서였습니다.

분할이 끝난 뒤에는 모든 조각을 다시 이어 붙여 원문과 일치하는지 검사했습니다. 문자가 누락되거나 순서가 달라지면 오류를 발생시켜 색인을 중단하도록 했습니다.

XLSX는 PDF와 다르게 처리했습니다. 각 행을 하나의 정보 단위로 보고 행 전체를 보존했습니다.

사용 데이터에서는 512토큰을 넘는 행이 없었습니다. 더 긴 행이 추가된다면 같은 문제가 발생할 가능성은 남아 있습니다.

## PDF 검토와 게시 기준

청킹 과정에서 원문이 달라지지 않았다고 해서 PDF가 정확하게 변환됐다는 뜻은 아닙니다.

Docling으로 PDF를 Markdown으로 변환할 때는 표의 구조가 달라지거나 OCR이 문자를 잘못 인식할 수 있습니다. 분할된 문자열을 다시 합쳐 원문과 비교하는 검증만으로는 이런 오류를 발견할 수 없습니다.

따라서 Docling으로 생성한 Markdown을 사람이 원본 PDF와 비교해 검토하고, 승인된 내용만 색인·게시하도록 했습니다.

실업인정 PDF 3종에서 생성한 339개 청크를 대상으로 검색 결과를 확인했습니다. 승인된 질문 14개를 기준으로 Recall@5는 62.38%, MRR@10은 0.5447이었습니다.

이 수치는 이후 변경사항을 평가하기 위한 기준선으로 기록했습니다.

사람이 검토하고 승인한 콘텐츠에는 원본 PDF와 연결되는 해시 정보를 기록했습니다. 색인과 게시 전에는 다음 항목이 일치하는지 확인했습니다.

- 청크 수
- 원본 PDF 해시
- 사람이 승인한 콘텐츠의 해시
- 출처 메타데이터

하나라도 일치하지 않으면 작업을 중단하도록 했습니다.

이 절차는 검토에 필요한 시간을 늘리지만, 변환 과정에서 발생한 오류가 승인 없이 게시되는 일을 줄이고 승인 후 내용이 변경됐는지도 확인할 수 있게 합니다.

## Evidence에서 원본 행까지 추적

검색된 정보가 원본 문서의 어느 부분에서 왔는지 확인할 수 있어야 답변의 근거를 검토할 수 있습니다.

이를 확인하기 위해 원본 데이터의 U-03 자료를 파싱하고 임베딩해 격리된 로컬 pgvector에 저장했습니다. 이후 게시된 데이터를 검색하고, Evidence에 기록된 출처를 따라 원본 엑셀의 행까지 추적했습니다.

대표 질문의 검색 점수는 0.781031이었고, 확인된 원본 위치는 다음과 같습니다.

`Source_V1.xlsx#SU_링크기록(전체)!A84:H84`

검색 결과에 출처 정보가 표시되는 것에서 끝나지 않고 실제 원본의 어느 부분을 참고했는지 확인할 수 있었습니다.

이후 검색 결과에 불필요한 내부 정보가 포함되지 않도록, 검색에 필요한 내용과 관리용 메모를 구분했습니다.

검색 본문에는 Source ID와 제목, 발췌만 포함하고 다음 필드는 제외했습니다.

- `condition`
- `unverified`
- `scope`
- `caution`

이 필드들은 내부 검토와 관리에 사용하는 정보로, 검색 결과의 본문에 그대로 노출할 필요가 없었습니다.

검증 기록에는 31개 항목 재색인 및 게시, 대표 검색 5건 성공, Evidence 25건 확인, 구버전 및 내부 메모 표제어 노출 0건이 남아 있습니다.

## 검색한 근거를 끝까지 확인할 수 있도록

이번 작업에서는 검색 결과를 잘 찾아내는 것만큼 그 결과가 모델에 전달될 수 있는 크기인지 확인하는 일도 중요했습니다.

청크를 나누는 과정에서 원문이 달라지지 않도록 검사하고, 사람이 승인한 내용만 게시하며, 검색된 정보가 어디에서 왔는지 추적할 수 있도록 정리했습니다.

결국 중요한 것은 검색 점수 하나가 아니라, **찾아낸 근거를 온전히 전달하고 다시 확인할 수 있는 구조**였습니다.
