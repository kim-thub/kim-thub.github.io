GitHub Taskflow:

이슈·브랜치·검사·PR을 이어 주는 Python CLI입니다. 팀 작업에서 stash/pop을 반복하던 문제를 자동화하되, 기존 변경과 기준 브랜치 보존을 먼저 검증했습니다.

반복 작업보다 위험했던 것은 작업 손실

팀에서 이슈와 PR을 만들 때, 진행 중인 파일 변경을 stash/pop으로 옮기는 절차가 반복됐습니다. staged·unstaged·untracked 변경이나 로컬 커밋이 남아 있을 때 자동화가 기존 작업을 덮거나 잘못된 기준에서 브랜치를 만들 가능성이 있었습니다.

이 도구는 작업 시작을 빠르게 만드는 동시에, 자동화를 허용하지 말아야 하는 Git 상태를 구분해야 했습니다.

잘못된 상태라면 이슈 생성 전에 중단

  • 기준 확인: --adopt는 기준 브랜치에서만 실행하고, 현재 HEAD와 원격 기준 브랜치의 조상 관계를 확인합니다.
  • 변경 보존: 현재 변경을 작업 브랜치로 옮긴 뒤 원래 기준 브랜치가 바뀌지 않았는지 검사합니다.
  • 부작용 차단: 예상하지 못한 로컬 커밋이나 feature 브랜치에서의 인수는 GitHub 이슈를 생성하기 전에 중단합니다.
Git 상태 확인→안전 조건 검사→작업 브랜치→검사·PR

Git 자체를 흉내 내지 않은 통합 테스트

임시 디렉터리에 실제 Git 저장소와 bare remote를 만들었습니다. 인덱스·브랜치·원격 기준은 실제 Git 명령으로 검증하고, 외부 GitHub 호출만 fake gh로 바꿔 사용자 계정에 영향을 주지 않았습니다.

변경 보존staged·unstaged·untracked 파일이 새 작업 브랜치에 남는 조건
기준 보호인수 후 원래 기준 브랜치가 바뀌지 않는 조건
오류 차단잘못된 상태에서 이슈를 생성하기 전에 멈추는 조건
18개 테스트 CI 실행 ↗공개 저장소 ↗

검증한 경계와 남은 범위

2026년 9월 21일 GitHub Actions에서 18개 테스트와 Python 컴파일 검사가 통과했습니다. 이 테스트는 실제 Git 상태를 다루지만 GitHub 호출은 대체했으므로, 실제 인증과 네트워크 장애까지 보증하지 않습니다.

AI와 함께 절차를 설계할 때도 최종 판단 기준은 설명의 그럴듯함이 아니라 실제 저장소에서 변경이 보존되는지였습니다.
