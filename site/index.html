데이터 적재와 응답의 신뢰성부터

예비 창업자가 매출·성장성·거래 활성도·경쟁 여건을 비교해 현장 조사할 상권을 좁히는 서비스입니다. 분기 데이터를 재수집해도 중복 저장되지 않아야 했고, AI가 설명에 사용한 숫자도 원천 지표와 일치해야 했습니다.

팀에서 맡은 일서울 Open API 적재와 upsert, Gemini 인사이트 수치 검증, DB 연결·예외 처리, 관련 회귀 테스트, 설계·API·문제 분석 위키 문서화
팀 결과React 화면과 서비스 전체 기능. 초기 UI 뼈대는 Stitch 시안을 바탕으로 Google AI Studio에서 생성한 코드가 포함됩니다.
개인 후속 작업별도 개인 저장소에서 FastAPI API를 Spring Boot로 이전하고 Projection, 계산 분리, 조회 범위 축소와 Spring Cache를 적용했습니다.

위키 문서 대부분은 AI의 도움을 받아 혼자 작성했습니다. 초기 UI 뼈대에도 생성형 AI를 활용했으며, 여기서는 팀의 화면 구현 전체와 개인의 문서·검증 작업을 구분했습니다.

팀 전체 기능을 개인 구현으로 표시하지 않습니다. 개인 후속 저장소는 비공개이므로 코드 링크를 공개 근거로 제공하지 않습니다.

기존 화면의 API 계약을 유지한 이전

기능을 새로 설계하기보다 React 화면과 Supabase PostgreSQL 데이터를 계속 사용할 수 있는 조건을 먼저 정의했습니다. 경로와 요청 파라미터, JSON 필드, null·빈 배열의 의미, 분석 점수와 추천 정렬을 유지 대상으로 뒀습니다.

React 화면→기존 /api/v1 계약→Spring MVC→JPA · Native SQL

Object[] 인덱스로 읽던 Native SQL 결과는 이름으로 접근하는 Projection으로 바꾸고, 분기 계산·퍼센타일·랭킹·숫자 포맷을 독립 함수로 분리했습니다. JUnit 5·Mockito로 계산 경계와 null 처리, 응답 구성을 확인했습니다.

배운 점. 중복 로직을 묶으면 수정과 테스트는 쉬워집니다. 그러나 여러 API가 같은 원격 데이터를 반복 조회하면, 코드 구조가 깔끔해져도 사용자가 기다리는 시간은 그대로일 수 있습니다.

SQL을 먼저 의심했지만, 전체 시간은 달랐습니다

진단 시 API 응답은 평균 약 30초였으나 Supabase의 EXPLAIN ANALYZE에서 핵심 SQL은 약 1.27초였습니다. Filter·AOP로 API 전체와 Repository 시간을 나누어 기록했고, 대량 데이터 전송과 동일 업종·분기 모집단의 반복 조회로 범위를 좁혔습니다.

SQL 실행 시간 하나만으로 전체 응답의 원인을 단정하지 않은 것이 구조 변경의 출발점이었습니다.

필요한 행을 좁히고, 반복 데이터를 재사용

변경 전: 큰 매출 행 집합 반복 조회→변경 후: 필요한 상권 조회+industry:quarter 캐시
  • 기본 추천의 상권 조회를 평균 1,650건에서 7건으로 줄였습니다.
  • Overview는 필요한 상권만 최대 약 21건 읽도록 제한했습니다.
  • 다섯 분석 API는 업종·분기를 키로 같은 모집단 데이터를 공유하도록 Spring Cache를 적용했습니다.

함수 공통화로 중복 로직을 줄이는 것과 원격 조회 비용을 줄이는 것은 다른 문제였습니다. 캐시는 적중할 때 여러 API가 같은 모집단 결과를 다시 사용할 수 있도록 적용했습니다.

조회 범위 개선과 캐시 적용은 서로 다른 단계의 비교입니다. Cold 응답에는 캐시 미적중 외에 서버 기동·DB 연결 상태가 함께 반영됐을 수 있습니다. 표시한 응답 시간은 TPS나 동시 부하 처리량을 뜻하지 않습니다.

현재 구현의 trade-off

실행 로그에서 ConcurrentMapCacheManager → ConcurrentMapCache → ConcurrentHashMap을 확인했습니다. 별도 캐시 서버 없이 프로세스 메모리에 저장되는 방식입니다.

MetricPopulationService@Cacheable(value = "metricPopulation", key = "#industry + ':' + #quarter")
얻은 점낮은 변경 범위

Redis 인프라를 추가하지 않고, 공통 서비스에 캐시를 붙여 반복 원격 조회를 줄였습니다.

감수한 제약프로세스에 종속

재시작하면 캐시가 비워집니다. 확인한 구성에는 TTL·크기 제한과 데이터 수정 후 제거 경로가 없어 오래된 값이 남거나 키가 늘 수 있습니다.

현재 Render Free 배포는 단일 인스턴스이므로 인스턴스 간 동기화는 현재 운영 조건에 포함되지 않습니다. 측정 기록으로 확인되는 성과는 요청 응답 시간과 조회 범위 변화입니다.

등록·분석 요청→크롤러 입력→유사도·감성·라벨→Gemini 요약→PocketBase 저장

크롤러 자체는 팀원이 맡았습니다. 분석 유스케이스에서 입력을 받아 유사 댓글 제거, 감성 분석, 라벨링, 요약 생성과 DB 관계 갱신 순서를 연결했습니다.

Flask 엔드포인트는 웹툰 등록·삭제·조회·분석 요청을 받아 유스케이스와 DB 함수를 호출하도록 구성했습니다.

예외 라벨이 통계와 생성 입력에 섞였습니다

분류 대상이 아닌 라벨 4의 댓글이 라벨별 집계와 Gemini 입력에 들어가면, 화면의 통계와 생성 요약이 서로 다른 범위를 설명할 수 있었습니다. 집계와 LLM 입력에서 동일하게 제외하도록 수정했습니다.

최신 회차가 이미 처리된 경우에는 중복 실행을 멈추고, 별점 크롤러가 만든 임시 레코드를 정리하도록 유스케이스를 바꿨습니다. LLM 요청 예외에 대한 재시도도 추가했습니다.

판단의 기준. 모델의 문장을 다듬는 일보다, 생성 입력과 저장되는 집계가 같은 데이터를 가리키는지가 먼저였습니다.

직접 실행해 확인한 범위

웹툰 등록·삭제, 분석 화면 이동, NLP 결과 파일 생성, PocketBase 저장을 한 흐름으로 직접 확인했습니다. 자동화 테스트와 처리 시간 비교 수치는 남아 있지 않아 테스트 자동화 또는 성능 향상으로 표현하지 않습니다.

모델 경로와 실행 환경이 로컬 설정에 의존합니다. 다른 환경에서 재현하려면 모델 준비 절차, 경로 설정과 테스트 데이터 정리가 필요합니다.

비공개 조직 저장소의 커밋·코드 링크는 방문자가 열 수 없으므로 이 공개 페이지에 근거 버튼으로 배치하지 않았습니다.
